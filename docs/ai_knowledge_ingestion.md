# Підготовка бази знань Околу до векторного пошуку

Джерело фактів — [ai_context.md](ai_context.md). Кожен заголовок `##` відділяє
одну самодостатню тему: питання для пошуку та відповідь про механіку Околу.
Тексти містять назву проєкту й уточнення меж застосування, щоб окремий фрагмент
залишався зрозумілим без сусідніх розділів. Python-описи інтентів, приклади
класифікації та інструкції імпорту не входять до індексованого документа.

## Експорт без звернення до БД або моделі

Із кореня backend-репозиторію:

```powershell
python -m app.export_ai_knowledge --output okil_knowledge.jsonl
```

Без `--output` записи друкуються у stdout. Формат — UTF-8 JSONL, один об’єкт
на рядок. Експортер перевіряє унікальні ID, метадані та наявність питання й
відповіді в кожному розділі. Команда не створює таблиць, не обчислює ембедингів,
не звертається до провайдерів і не завантажує записи в БД.

```json
{"category":"project","content":"Окіл: призначення та команда\n\nПитання: ...\n\nОкіл ...","metadata":{"document_id":"okil-mechanics","chunk_id":"okil.overview","title":"Окіл: призначення та команда","source_document":"ai_context.md","language":"uk","reviewed_at":"2026-11-12","source_revision":"42de2eb","code_sources":["frontend:src/components/footer.tsx"]}}
```

## Поля та подальше завантаження

Імпортер читає Markdown без проміжного JSONL. Потрібні встановлені залежності
з `requirements.txt` і `DB_URL` у `.env` для Neon із правом запису.
Перший запуск MiniLM може завантажити модель; окремий API-ключ не потрібен.

```powershell
# Перевірка структури без моделі та БД
python -m app.import_ai_knowledge --validate-only

# Створення векторів без підключення та запису в БД
python -m app.import_ai_knowledge

# Створення векторів і запис у наявну таблицю Neon
python -m app.import_ai_knowledge --apply
```

За замовчуванням джерело — `docs/ai_context.md`. Інший файл у тому самому
форматі задається через `--source шлях/до/файла.md`.
Успішний запис завершується повідомленням `Import committed` із кількостями
доданих, оновлених і незмінених записів. Без `--apply` запису немає.

- `category` — тема до 50 символів для `AIKnowledge.category`. Це не інтент
  користувацького питання: формулу можуть знайти питання `hex_score`, а загальне
  пояснення — `project_info`.
- `content` — текст для ембедингу: заголовок, типові питання та фактична відповідь.
  Індексувати потрібно весь цей текст; не лише заголовок або список питань.
- `metadata` — походження, стабільний `chunk_id`, мова, ревізія коду й дата
  перевірки документа. В ORM це поле називається `AIKnowledge.metadata_json`,
  у самій БД — `metadata`.

Для `ai_knowledge.embedding` потрібно окремо створити **384-вимірний** вектор
кожного `content` моделлю `paraphrase-multilingual-MiniLM-L12-v2`.
Запити пошуку кодуються тією самою моделлю, версією та налаштуваннями,
що й фрагменти. Класифікатор використовує цю ж розмірність, але його центроїди
інтентів не є векторами фрагментів документації. Після зміни embedding-моделі
переіндексовується весь набір; змішувати її вектори зі старими не можна.

Зміна ORM-константи не змінює наявну колонку PostgreSQL через `create_all`.
Перед імпортом потрібно перевірити фактичний тип `ai_knowledge.embedding`:
він має бути `vector(384)`. Якщо колонка має іншу розмірність, потрібна окрема
міграція. Вектори іншої розмірності не можна просто обрізати або доповнювати:
їх потрібно перестворити з вихідних текстів тією самою MiniLM.
Імпортер перевіряє фактичний тип колонки перед записом і не змінює схему.

Імпортер зіставляє записи за парою `document_id + chunk_id` і оновлює текст,
метадані та вектор в одній транзакції. Повторний запуск не додає дублікати.
Оскільки unique constraint для цієї пари відсутній, імпортер використовує
транзакційне advisory-блокування документа; інші програми запису мають
дотримуватися того самого протоколу. Якщо дублікати вже є, імпорт зупиняється.
Незмінені записи не перезаписуються. Сторонні документи та старі теми,
видалені з Markdown, не видаляються автоматично: їх очищення — окрема дія.

Для chunking використовуй межі `##`, а не довільну кількість символів.
Не розділяй формулу з її умовами або застереження про різницю чату й мапи.
Якщо MiniLM не вміщує розділ, імпортер ділить текст для кодування на вікна,
кожне з яких перевірене її tokenizer на `max_seq_length` зі спеціальними токенами.
Вектори вікон нормалізуються, усереднюються та знову нормалізуються.
У БД зберігається один вектор і повний текст розділу; хвіст не обрізається.
У метадані додаються модель, розмірність, стратегія, кількість вікон і SHA-256
тексту. Для довгих пошукових питань потрібно застосовувати ту саму стратегію;
коротке питання має одне вікно та звичайний нормалізований MiniLM-вектор.

## Використання результатів пошуку

Передавай до моделі знайдені `content` разом із `chunk_id` та походженням.
Статична база пояснює механіку; поточні POI, бали, ваги й маршрути для конкретної
ділянки беруться з відповідних сервісів. Відсутність релевантного фрагмента —
підстава уточнити питання або сказати, що відповіді немає в доступних даних.
Дата перевірки документа не є датою оновлення всіх POI.

У поточному `app.ai_assistant.get_project_information` пошук `ai_knowledge`
ще не реалізований: функція читає лише короткий опис і каталог типів.
Експорт JSONL сам по собі не підключає retrieval до відповідей чату.

Перед використанням перевір питання на кшталт «чому нульовий рейтинг»,
«що входить у здоров’я», «як рахуються ваги», «чому оцінка чату інша»,
«чим HERE відрізняється від TravelTime». Оцінюй відповідність знайденого
фрагмента й фактичність відповіді, а не лише близькість векторів.
