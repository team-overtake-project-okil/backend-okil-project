# Пояснення доступності без повторного розрахунку оцінок

Генератор формує до трьох речень: кількість об’єктів у радіусі максимального
дистанційного бала, найближчі відстані та висновок про перевищення порога.
Наявний бал категорії не перераховується. Текст описує методику й фактичну
доступність, а не точне походження збереженої цифри.

Фінальні оцінки в API, CLI та при записі job округлюються до цілих,
половини — в більший бік (`88.5 → 89`). Відстані в тексті — до цілих метрів,
від 1 км — до двох знаків у кілометрах, без зайвих нулів. Якщо округлення
приховує невелике перевищення радіуса, текст уточнює «понад 200 м».
Радіусна належність, проміжні бали, нормалізовані ваги й геометричний
розрахунок використовують початкову точність; округлення застосовується
тільки до фінального значення. `adjusted_score` залишається технічним
множником із двома десятковими знаками, а не цілим балом категорії.

Приклад:

> У радіусі 200 м для максимального бала є 4 аптеки, найближча — за 150 м.
> Супермаркетів у межах 300 м для максимального бала не знайдено, найближчий —
> за 320 м; банків або банкоматів у межах 300 м для максимального бала не знайдено,
> найближчий — за 450 м. Віддаленість об’єктів за межами цих радіусів не дає
> максимального бала за відстань.

Кількості й відстані у вступному прикладі умовні; радіуси відповідають звірці
`point_types`. API використовує фактичний `radius_of_influence_1`
з `point_types`. Відстані — по прямій від центру гексагону, за тією самою
локальною апроксимацією для Львова, що й у чинному job.

## API

`GET /hexagons/{h3_id}` повертає попередні поля категорій і тільки одне нове
поле — `explanation`. Поля `score_explanation`, `score_breakdown`, `types_data`,
`calculated_score`, `score_matches_stored` прибрані з відповіді.

Шлях запиту:

1. Читання збережених балів гексагону.
2. Один SQL-запит до типів, POI та зупинок: радіус, кількість у ньому,
   мінімальна відстань без обмеження цим радіусом.
3. Підготовка JSON і генерація тексту без розрахунку будь-яких балів типів.
4. Повернення збережених балів, загального рейтингу за користувацькими
   вагами та пояснень.

Разом два запити БД, без читання маршрутних зв’язків і N+1-запитів за типами.
Для відсутнього гексагону повертається 404 до читання POI. `GET /hexagons`
як раніше повертає список рейтингів без пояснень.

Схема БД не змінюється, запит не перезаписує збережені оцінки. У пакетному job
формули залишилися попередніми; фінальне округлення уніфіковано через
`round_final` (половини в більший бік). Немає JSONB,
повторного розрахунку, розкладу числових втрат чи перевірки `stale`.
Оновлення збережених оцінок залишається обов’язком наявного job.
Загальний рейтинг за користувацькими вагами як і раніше обчислюється при запиті
зі збережених категорійних балів.

Мобільність описує відстань до зупинок і додає уточнення про транспортні
зв’язки. Близька зупинка не оголошується гарантією максимального бала мережі;
маршрути та транспортний бал для пояснення не перераховуються.

## CLI — команда не змінюється

```powershell
python -X utf8 -m app.category_narratives examples/category_scored_cases.json
```

Назва `category_scored_cases.json` збережена для сумісності команди, але
демонстраційні дані тепер не містять балів типів чи їхніх ваг. Оригінальний
`examples/category_test_cases.json` також підтримується. Обидва файли прикладів
тепер містять усі 8 категорій і 25 типів із `point_types`, із фактичними
радіусами та відстанями для H3 `891e7688377ffff` на 2026-11-06.
Початковий JSON користувача залишений у тестовій фікстурі для сумісності.
У вхідних даних `closest_radius_m`
трактується як потрібний радіус оцінювання, а не довільний більший радіус пошуку.
Число `num_objects_in_radius` обов’язково має бути пораховане саме в ньому.

Тільки тексти в PowerShell:

```powershell
python -X utf8 -m app.category_narratives examples/category_scored_cases.json |
    ConvertFrom-Json |
    ForEach-Object {
        Write-Host "`n$($_.category_name) — $($_.score)/$($_.max_score)"
        Write-Host $_.explanation
    }
```

Python-інтерфейс залишається `explain_category(category)` та
`explain_categories(test_cases)`. Вихід: `category_name`, `score`, `max_score`,
`explanation`. За замовчуванням описуються до чотирьох типів: найближчий,
найбільше відносне перевищення порога та решта за відстанню. `--max-types 20`
дозволяє включити всі типи, зберігаючи до трьох речень, але збільшує їх довжину.

## Дані та перевірка

Вхідний JSON зберігає початкові поля `category_name`, `score`, `max_score`,
`weight`, `types_data`. Для типу потрібні `type_name`, `num_objects_in_radius`,
`closest_radius_m`, `nearest_point_dist_m`. Додатковий `score_basis=gtfs_network`
використовується сервісом для зупинок. Старі `type_score` і `type_weight`
ігноруються, а не обчислюються чи перевіряються через зворотний розрахунок.
Якщо переданий `full_score_radius_m`, він має дорівнювати `closest_radius_m`:
кількості з більшого радіуса не можна приписувати меншому.

Невідома відстань — `null`, не нуль. Нульова відстань допустима, межа радіуса
включена. Нуль об’єктів означає «не знайдено за наявними даними», а не доказ
їх фізичної відсутності. Без конфігурації типів категорія отримує повідомлення
про недостатність даних. Відповідність збереженого бала поточним POI не
перевіряється, тому текст не приписує йому точних числових причин втрат.

`config.py` містить українські форми назв, `templates/*.j2` — формулювання,
`generator.py` — вибір фактів, `repository.py` — SQL, `service.py` — підготовку.
Змінювати категорійні `if/else` для додавання нових типів не потрібно.

Коди типів, категорії та всі пороги звірено з Neon: див.
[point_type_catalog.md](point_type_catalog.md). Радіуси в API читаються тільки
з `point_types`, без запасних значень у SQL; невідомий або некоректний радіус
не підміняється вигаданим. Словники назв централізовано в `config.py`.

```powershell
python -m pytest tests/test_category_narratives.py tests/test_category_narrative_format.py tests/test_hexagon_explanations.py tests/test_hexagon_scoring.py -q
```
