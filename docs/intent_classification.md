# Інтенти Околу: сценарії, межі та перевірка

`app.intent_classifier.INTENT_DESCRIPTIONS` адаптовано з розгорнутих описів
до поточної embedding-класифікації. MiniLM обчислює семантичну близькість,
а не виконує інструкції в описі. Тому кожен опис складається з коротких
позитивних сценаріїв і природних питань без довгих виключень про чужі інтенти.

## Як використовуються розширені описи

Порожній рядок `\n\n` розділяє сценарії. `IntentClassifier.create` кодує кожен
сценарій окремо, нормалізує вектор та усереднює сценарії одного інтенту.
Класифікація порівнює питання з трьома отриманими центроїдами через cosine
similarity. API `classify`/`parse_query`, розмірність 384 та поріг 0.2 збережено.
Оцінка близькості не є ймовірністю. Низька близькість дає `intent=None`.

Короткі сценарії потрібні, щоб не передавати весь довгий опис як один вхід,
кінець якого може обрізати embedding-модель. Новий сценарій має описувати
одну тему кількома короткими реченнями, з прикладами формулювань користувача.
Не додавай довгих переліків чи вимог до генерації відповіді в один сценарій.
Після зміни описів перезапусти процес, який кешує класифікатор.

Це не навчені правила й не гарантія точнішої класифікації. Потрібне порівняння
попередньої та нової версій на однаковій моделі та реальних питаннях.
Модульні тести з підставними векторами перевіряють обробку сценаріїв,
математику й контракти; вони не вимірюють якість MiniLM.

## Семантичні межі

- `poi`: результатом мають бути реальні місця, кількість, розташування,
  відстань, маршрут до місця або властивості конкретного закладу.
- `hex_score`: результатом мають бути бал, порівняння оцінок, пояснення
  формули, ваг, округлення або впливу інфраструктури на рейтинг.
- `project_info`: призначення проєкту, користування, загальний зміст
  категорій, джерела, покриття, обмеження та проблеми роботи сервісу.

Згадка «школа» не означає автоматично `poi`: «чому школа не підняла бал» —
`hex_score`, а «що входить в освіту» — `project_info`.
Наявність обраного гекса не робить загальне питання про проєкт питанням про бал.
Пошук непідтримуваного типу залишається `poi`; відповідь має пояснити межі даних.
Привітання й сторонні теми не є четвертим предметним інтентом і не повинні
примусово перетворюватися на `project_info`: чинний контракт підтримує `None`.

`parse_query` ділить текст за пунктуацією та деякими сполучниками й класифікує
отримані частини. Змішаний запит може дати кілька інтентів; нерозділена складна
частина все ще отримує один інтент. Не можна вважати regex повноцінним
семантичним поділом. У classifier не передається історія: питання «а найближча?»
без попередньої теми не гарантує коректного розпізнавання. Chat-adapter окремо
відновлює H3 та має вузькі корекції явних проєктних і рейтингових питань.

Загальна формула семантично належить до `hex_score`, але поточний chat-adapter
вимагає H3 для всіх запитів цього інтенту. Інтент не означає, що потрібні дані
або можливість дії вже доступні. Довільний радіус, години роботи, порівняння
кількох H3 та користувацькі ваги не реалізуються самим розширенням описів.

## Контрольні запити для реальної моделі

Це очікувані семантичні мітки, а не звіт про пройдений model eval.
Для ручного запуску використовуй `python -m app.try_intent_classifier` із
налаштованою моделлю; оцінюй окремо сирий classifier і корекції chat-adapter.

| Запит | Очікуваний інтент | Що перевіряємо |
| --- | --- | --- |
| Що є в цьому гексі? | `poi` | Загальний пошук місць |
| Де найближча аптека? | `poi` | Близькість об’єкта |
| Скільки шкіл до 500 метрів? | `poi` | Кількість і радіус |
| Де купити продукти біля дому? | `poi` | Потреба без коду типу |
| Знайди кав’ярню поруч із вокзалом | `poi` | Харчування й локація |
| Куди піти з дитиною? | `poi` | Підбір місць за потребою |
| Де тренуватися поруч? | `poi` | Спортивні об’єкти |
| Де найближче укриття? | `poi` | Об’єкт, а не бал безпеки |
| Які автобуси їдуть із цієї зупинки? | `poi` | Маршрутні дані |
| Коли приїде наступний автобус? | `poi` | Не вигадувати час без джерела |
| Як дістатися до цього музею? | `poi` | Маршрут до конкретного місця |
| О котрій зачиняється ця аптека? | `poi` | Властивості закладу |
| Яка адреса й телефон магазину? | `poi` | Конкретні поля, яких може бракувати |
| Знайди парк або ветклініку поруч | `poi` | Межі поточного каталогу |
| Де більше шкіл: біля А чи Б? | `poi` | Порівняння об’єктів без рейтингів |
| Знайди кафе біля гекса з балом 80 | `poi` | Бал лише описує локацію |
| Який рейтинг цього гекса? | `hex_score` | Загальний бал |
| Чому тут 42, а поруч 75? | `hex_score` | Порівняння чисел |
| Що знижує оцінку цієї ділянки? | `hex_score` | Складові бала |
| Чому низька освіта, хоча школа поруч? | `hex_score` | Відокремлення від пошуку шкіл |
| Чому біля зупинки мобільність не 100? | `hex_score` | Відокремлення від пошуку зупинок |
| Порівняй А і Б для сім’ї за індексом | `hex_score` | Персональні пріоритети |
| Як рахується індекс комфорту? | `hex_score` | Формула без конкретного гекса |
| Чому це не середнє арифметичне? | `hex_score` | Геометрична формула |
| Як відстані перетворюються на бали? | `hex_score` | Дистанційна формула |
| Чому нуль категорії обнулив рейтинг? | `hex_score` | Активна нульова складова |
| Що буде з індексом, якщо вимкнути їжу? | `hex_score` | Вага й нормалізація |
| Як зміниться бал із пріоритетом транспорту? | `hex_score` | Сценарій зміни ваги |
| Що означає adjusted_score? | `hex_score` | Поле розрахунку |
| Чому 88.5 округлилося до 89? | `hex_score` | Округлення |

| Чому оцінка чату відрізняється від мапи? | `hex_score` | Джерела мобільності та ваги |
| Що таке Окіл і для кого він? | `project_info` | Призначення |
| Хто створює OKIL? | `project_info` | Команда |
| Що таке гекс і h3_id? | `project_info` | Будова сітки |

| Які категорії є в проєкті? | `project_info` | Каталог |
| Що входить у здоров’я? | `project_info` | Загальний зміст категорії |
| Чому аптеки у щоденних потребах? | `project_info` | Розподіл типів |
| Де відкрити пріоритети? | `project_info` | Інструкція UI, а не вплив ваг |
| Як знайти адресу на мапі? | `project_info` | Користування |
| Як часто оновлюються дані? | `project_info` | Актуальність |
| Звідки дані про укриття? | `project_info` | Джерела |
| Чи враховано шум і повітря? | `project_info` | Межі показника |
| Відстань до POI по прямій чи пішки? | `project_info` | Загальна механіка відстаней |
| Навіщо сервісу HERE та TravelTime? | `project_info` | Можливості проєкту |
| Чи гарантує бал безпеки відкрите укриття? | `project_info` | Межі висновків |
| Мапа не відкривається | `project_info` | Проблема сервісу |
| Чому мого магазину немає в базі? | `project_info` | Повнота даних |
| Дай рецепт сирників | `None` | Стороння тема, поріг потрібно виміряти |
| Напиши вірш про космос | `None` | Відсутність примусового fallback |

Окремо перевіряй змішані питання: «поясни оцінку гекса і знайди школи»
має дати дві релевантні частини; «поясни оцінку гекса і дай рецепт сирників»
має зберегти питання про оцінку та відхилити рецепт. Семантично невизначене
«а здоров’я?» потребує контексту або уточнення, а не наперед заданої мітки.

Фіксуй помилки між парами `poi/hex_score`, `hex_score/project_info` і помилкове
прийняття сторонніх тем. Зміна кількості сценаріїв може змінити близькість,
тому придатність порога 0.2 потрібно повторно оцінити на реальних запитах.
